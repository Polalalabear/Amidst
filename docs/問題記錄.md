# Portable Blender Asset Roots — 問題記錄

## English

Document status: `CONFIRMED` implementation record

Repository classification: `PUBLIC_ALLOWED`

### What was done

- Added machine-local resolution for `blender-source`, `blender-textures`,
  `blender-working`, and `blender-output`.
- Updated Blender scripts to resolve assets through those logical roots instead
  of assuming that large private files exist inside each Git worktree.
- Added source checksum snapshots, task-specific atomic output locks, a local
  root health check, and migration manifest contract v0.2.0.
- Added macOS, Windows, and Linux setup and verification instructions.

### What problem this solves

Large private Blender assets no longer need to be duplicated across Codex
worktrees. A macOS absolute path, Windows drive letter, Linux mount point,
symlink target, or junction target is no longer used as artifact identity.
Read-only sources are checked for mutation, and two writers cannot silently use
the same task output directory.

### How it works

Runtime root precedence is environment variable, ignored
`local/asset_roots.json`, then the repository-local compatibility fallback.
Portable records use `asset://<root-alias>/<relative-path>`, byte size, and
SHA-256. Physical roots remain local. Before and after a derived-file operation,
the source checksum is compared. A task acquires `.amidst-task.lock` atomically
before writing and releases it after completion. The health check confirms root
availability, read-only intent, and an isolated output write probe without
printing the physical paths.

### Boundary and current status

The resolver, guards, lock, documentation, and automated tests are implemented.
macOS code and Blender embedded-Python checks passed. Windows and Linux commands
are documented but remain `OPEN` until executed on those systems. No private
asset was moved or published, no Ground Truth was changed, and no new pilot was
rendered. This change improves portability and integrity; it does not resolve
the separate EEVEE composition or observation-render validity issue.

## 繁體中文

文件狀態：`CONFIRMED` 實作紀錄

Repository 分類：`PUBLIC_ALLOWED`

### 做什麼

- 新增 `blender-source`、`blender-textures`、`blender-working`、
  `blender-output` 四個本機 logical root resolver。
- Blender 腳本改由 logical root 尋找資產，不再假設大型私人檔案一定存在每個
  Git worktree 內。
- 新增來源 checksum snapshot、task-specific atomic output lock、本機 root
  health check 與 migration manifest v0.2.0。
- 補齊 macOS、Windows、Linux 的設定與驗證指令。

### 解決什麼

大型私人 Blender 資產不必在多個 Codex worktree 重複保存。macOS absolute
path、Windows drive letter、Linux mount point、symlink target 或 junction target
不再作為 artifact identity。來源檔會受到唯讀與內容異動檢查；兩個 writer 也
不能無聲地寫入同一個 task output directory。

### 怎麼解決

Runtime 依序採用環境變數、ignored 的 `local/asset_roots.json`、repository-local
相容 fallback。可攜式紀錄使用 `asset://<root-alias>/<relative-path>`、byte size
與 SHA-256，實體 root 只留在本機。Derived-file 操作前後會比較 source checksum；
task 寫入前以 atomic 方式取得 `.amidst-task.lock`，完成後釋放。Health check 會
確認 root 是否存在、來源的唯讀意圖，以及隔離的 output write probe，而且不輸出
實體路徑。

### 範圍與目前狀態

Resolver、guard、lock、文件與自動測試皆已實作；macOS 程式與 Blender embedded
Python 檢查已通過。Windows 與 Linux 指令已完成文件化，但實機執行前維持
`OPEN`。本次沒有搬移或發布私人資產、沒有修改 Ground Truth、也沒有產生新
pilot。本變更解決的是可攜性與完整性，不代表已解決另外的 EEVEE composition
或 observation-render validity 問題。
